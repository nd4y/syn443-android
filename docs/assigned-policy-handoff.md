# Assigned policy handoff

The controller exposes bounded asynchronous begin/finish/abort transitions for the native integration. Each request carries the login generation, signed-policy receipt and activation generation; admission alone never authorizes a candidate. Encryption and engine validation run on its worker before the current-intent CAS and immutable-view publication. An accepted abort invalidates the view before enqueue. A replacement policy or logout rejects late results. On controller recreation, an interrupted applying journal is durably rolled back before any view or network refresh can publish it. The [enrolled VPN integration](enrolled-vpn.md) connects these internal commands to the real TUN supervisor.

Assignment receipt and protected storage are the foundation of the [enrolled VPN path](enrolled-vpn.md). Explicit Connect, bounded refresh on a separately bound physical Network and native-owner retirement use this journal. Full physical acceptance and managed overlay namespaces remain separate gates. Existing M1 operator-provisioned activation remains a distinct authority.

`Assignments` binds every policy journal to the exact login generation, bootstrap authority, device ID and proof-key thumbprint. It verifies the pinned signature and device/key claims again, uses the conservative HTTPS time window, and accepts only capabilities currently advertised by enrollment. A new identity cannot inherit a previous account's activation history or configuration. A management release is not admitted through this enrollment path.

The handoff has two durable writes. First, the encrypted assignment journal records the verified desired/candidate policy. Then the login intent records the envelope hash as its receipt. Until both agree, the candidate cannot be consumed. A same-generation recovery may reverify the journal and repeat the receipt step. A cancelled, replaced or reauthenticated identity cannot finish an old handoff. The first candidate has no unsigned local configuration fallback. Subsequent candidates use the existing activation checks and last-known-good rollback rules; failed snapshots and revocation floors still apply.

The assignment ciphertext has its own authenticated-data domain and includes namespace, login generation, authority, device and key. Its bounded 2MiB record contains policy activation snapshots, without copying session credentials. Credentials and public metadata retain their 64KiB bounds. Crypto stays on the bounded worker, outside the intent lock. A prepared write must pass the same current-intent check before persistence, and its bytes are independently read back. Logout removes both credential and assignment ciphertext before retirement acknowledgement. An orphaned assignment cannot be treated as a fresh signed-out state.

The controller fetches the policy after registration and on an explicit retry/recovery. A pending publisher response remains visible as provisioning, with no implicit Connect. The enrolled service separately admits bounded periodic refresh. Near access-token expiry, refresh persists its exact operation before dispatch. A lost rotated-session reply retries the same body and old credential within the existing retry window. After a device reboot, a fresh pinned issuer discovery supplies a proof-time anchor; the API must still validate the old refresh token and return a rotated session before any assigned policy is accepted.

Seven JVM methods exercise scope/time/capability fences, interrupted handoff, activation/rollback and retirement prerequisites. Six additional Android cases exercise real encrypted storage, cancellation after prepared encryption, namespace/generation/device/key substitution, oversized/orphaned data, controller recovery with a real signed policy, wrong-key rejection, and refresh response loss. These tests do not claim real external-browser enrollment or native managed-policy activation.

The core compiles a worker-verified `AssignmentPermit` for an applying or active policy. Consumers recheck the current identity, receipt, activation generation, selected envelope, revocation floor and security epoch without disk/crypto work. Its deadline uses the conservative monotonic time window; an applying candidate is also bounded by its activation deadline. A new valid policy cannot revive an expired native reader or silently replace a different identity/configuration in the same owner. `RuntimePolicies` supplies this lease to Android native activation.

Activation begin records boot and elapsed deadline. Late successful checks and checks from another boot roll back instead of committing. Recovery can poison an interrupted candidate from its authenticated journal without relying on wall time, preserving failed snapshots and last-known-good authorization requirements. Worker/facade and cross-process test paths are described in [enrolled-vpn.md](enrolled-vpn.md); physical acceptance remains distinct.

Zero/default activation fields are omitted from the canonical assignment encoding, preserving the exact previous encrypted cache format. Nondefault candidate deadlines are serialized and authenticated; abort/finish clears them. A regression checks both pre-activation compatibility and applying-state persistence.

Android now prepares an immutable runtime view on the identity worker and publishes it only under the current-generation fence after persistence. Restart may reconstruct it from protected state; Cancel/reauthentication clears it immediately. Status exposes only phase/revision/validation flags. Config/lease reads use the verified view and boot/monotonic clocks without application-file or Keystore access, but the native service remains unconnected to this view. Managed NetBird configs cannot validate as candidates until an account credential namespace is implemented, even if their declared capability list omits NetBird.
