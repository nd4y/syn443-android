# Android release packaging

The `jvm-and-apk` job in GitHub Actions builds the normal Android release variant and uploads `syn443-unsigned-release-input`. The archive contains `app-release-unsigned.apk` and `inventory.json`. Use the Actions run and source commit to identify a candidate.

Push and pull request builds are generic. A manual release build inherits the same explicitly public installation profile and link host as the normal first-run bootstrap. The existing public-profile gate validates this input before either APK is built. A signed descriptor may include the mobile administrative bootstrap. Its API origin and issuer pass the public endpoint checks, and its client ID, audience and assurance level must match the mobile administrative protocol.

The job decodes the packaged manifest, compares its application version with the Android Gradle Plugin output, checks the supported SDK and verifies that the VPN still requires Android's system permission. It checks that the release control provider is private and that debug-only components, backup, instrumentation and default cleartext access are disabled. It also checks APK alignment and ELF load segments for 16 KiB pages, runtime assets, both native ABIs and equality of the engine library bytes with the input AAR. The two release ART profiles must match the separate binary and metadata generated by the pinned Android Gradle Plugin byte for byte. Privacy and secret scans precede upload.

The inventory records APK size, SHA-256, package, version, supported SDK, native library digests and the engine and shared-contract lock hashes. The independent release signer takes these exact bytes as input. Signing changes the APK digest. The final distribution manifest must identify the signed file and its signer before an update is offered to users. This artifact is intended for the signing stage. The emulator suite continues to consume its own debug instrumentation packages.

## Verify the signed APK

After independent signing, use the unsigned APK and its SHA-256 from the accepted Actions input. Obtain the public certificate fingerprint from the operator's existing signing record. Supply both digests to the verifier.

```sh
python3 tools/verify_signed_apk.py --unsigned app-release-unsigned.apk --signed app-release.apk \
  --unsigned-sha256 "$EXPECTED_INPUT_SHA256" --signer-sha256 "$EXPECTED_CERT_SHA256" \
  --apksigner "$ANDROID_HOME/build-tools/36.0.0/apksigner"
```

The tool checks the SDK signature and signer, then compares the name, size, compression method and bytes of every original APK entry. It then runs the SDK alignment check on the same signed snapshot. The uncompressed native libraries must have 16 KiB ZIP alignment. Supply the `apksigner` path from an Android SDK Build Tools installation containing `zipalign`. The receipt includes the digest and size of the final signed file. Use a v2/v3 signing block with v1 signing disabled for this release workflow. A certificate rotation needs the independently approved successor pin. Distribution still requires a signed release manifest and Android's user installation flow.

GitHub Actions signs a normal release with a temporary test identity to exercise these checks. The public evidence records only the source, version and scenario results. The test key and test-signed APK are removed with the temporary directory.

The same job builds the pinned Control Plane `apk-release` tool. It issues two addressed metadata revisions for the SDK-verified file using a separate disposable metadata key. After deleting that key, it verifies both revisions, repeats the accepted revision and rejects an older revision, another recipient and a different file signed by the same APK signer. The uploaded receipt contains the scenario names. The test files remain on the runner until the fixture exits.

## Verify an update on Android

On the home screen, open **Обновление приложения**. A managed installation profile with version 3 carries a public `releaseAuthority` containing the service ID, channel and an independent P-256 verification anchor. This field is distributed inside the installed APK. The device borrows the current policy's capability list, evaluator, schema and trusted time from its enrolled session. Older installation profiles keep their existing bootstrap and have no configured update channel.

Select the addressed JWS manifest and then the APK. The app checks the offered revision, its recipient, channel, minimum upgrade version, Android SDK and ABI. It copies and hashes the selected file in a private directory and uses Android's package parser to check the signing certificate, version and SDK. The embedded engine libraries must match the signed per-ABI hashes. An older revision or a conflicting offer at the same revision cannot supersede the encrypted local record.

Tap **Перейти к установке** to hand the verified file to the Android system installer. Android may first ask you to allow SYN443 as an installation source. After returning, tap the installation button again. The app rechecks the file, current enrollment, policy and revision before handoff. Closing the screen or cancelling installation preserves the running configuration and enrollment. Final acceptance of the release update on an enrolled physical device is tracked separately.
